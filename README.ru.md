# DeepSeek PR Review

[English](README.md) | [Русский](README.ru.md)

GitHub Action, который делает ревью pull request с помощью [pr-agent](https://github.com/qodo-ai/pr-agent) и DeepSeek. Ревью публикуется от имени вашего бота (GitHub App), поэтому сразу видно, что комментарии оставил ревьюер, а не `github-actions[bot]`. Ещё бот может ставить approve, если ревью чистое.

## Что делает

1. Пропускает черновики (draft) и PR от авторов, которым вы не доверяете (см. [Чьи PR проверяются](#чьи-pr-проверяются)).
2. Получает для бота короткоживущий токен. Токен действует только в текущем репозитории.
3. Запускает pr-agent в контейнере. Он читает diff через GitHub API и публикует общий комментарий и замечания к строкам. Код из PR не скачивается и не запускается. Файлы с данными в ревью не попадают (см. [Файлы с данными](#файлы-с-данными)), а модель видит свои прежние замечания и ответы в их закрытых обсуждениях, поэтому не повторяет их другими словами. Если попытка упала или не записала читаемый обзор, например когда API DeepSeek оборвал соединение, обзор запускается снова, до `review-attempts` раз. Если упали все попытки, шаг завершается ошибкой.
4. Ставит approve, если выполнены все условия:
   - вердикт модели `no_concerns_found`;
   - нет ни ключевых замечаний, ни проблем безопасности;
   - все изменённые файлы, кроме оставленных в стороне файлов с данными, проверены полностью, и ни один не оказался слишком большим, чтобы передать его модели (см. [Файлы с данными](#файлы-с-данными));
   - ни один изменённый файл не подпадает под `approval-excluded-paths` (по умолчанию `.github/*`: изменения CI одобряет человек);
   - пока шло ревью, последний коммит PR не изменился.

   После первого ревью PR следующие ревью сходятся (`converge`): approve блокируют только замечания на строках, добавленных или изменённых после прошлого ревью бота, и его собственные прежние обсуждения, которые никто не закрыл. Замечание, повторённое на уже проверенном коде после того, как человек ответил и закрыл обсуждение, больше не блокирует. Вердикт модели — только рекомендация, если ни одно её замечание не блокирует; если замечаний нет совсем, вердикт по-прежнему блокирует. Проблемы безопасности, не полностью проверенные файлы и защищённые пути по-прежнему блокируют.

   Чтобы PR не ходил по кругу, следующее ревью также не блокируют:
   - замечание, которое повторяет прежнюю мысль бота в том же файле, в том числе другими словами, если то обсуждение ещё открыто (оно блокирует само) или его закрыл человек;
   - открытые обсуждения бота по замечаниям, которые не блокировали, когда их написали, или по файлам, не попавшим в ревью;
   - любые замечания модели, когда уже `max-blocking-reviews` (3) ревью этого PR приняли решение. Замечания по-прежнему публикуются и перечисляются; проблемы безопасности, не полностью проверенные файлы, открытые обсуждения бота с прежних ревью и защищённые пути по-прежнему блокируют.

   Следующее ревью также сообщает модели, что автор ответил на прежние замечания, поэтому она сообщает только о подтверждённых дефектах, в основном в изменённом коде, и не поднимает снова то, на что уже ответили.

   Approve ставится на конкретный проверенный коммит. Во всех остальных случаях бот снимает (dismiss) свои прежние approve. Если ревью упало с ошибкой, бот тоже их снимает. Ревью людей он никогда не трогает.
5. По желанию (`request-changes: "true"`) ставит «request changes», если вердикт модели `changes_required`. Более поздний approve бота отменяет этот запрос. Более поздний завершённый обзор с мягким вердиктом снимает его. Упавший обзор оставляет запрос в силе, поэтому заблокированный им мерж остаётся заблокированным.

6. Закрывает свои обсуждения, которые исправил следующий коммит (`resolve-fixed-threads`): строки, на которые указывало обсуждение, изменились или удалены, а ревью нового коммита не повторило там замечание. Бот отвечает один раз после закрытия. Если закрыть исправленное обсуждение не удалось, оно не мешает approve, а итоговый комментарий просит человека с правом записи закрыть его.
7. Поддерживает один комментарий с итогом: что бот решил по последнему коммиту и список того, что исправить до его approve:
   - каждое блокирующее замечание со ссылкой на файл и строки;
   - каждое прежнее обсуждение, которое ещё открыто, со ссылкой на него;
   - любой другой блокер, например проблемы безопасности или не полностью проверенные файлы.

   Ниже списка перечислены неблокирующие замечания, файлы с данными, которые стоит посмотреть человеку, и обсуждения, которые бот закрыл сам. Комментарий обновляется при каждом ревью, а не добавляется заново.

Approve бота — это сигнал, а не гарантия. Модель может пропустить ошибку, а текст PR может пытаться её обмануть. Всё важное по-прежнему проверяет человек.

Модели сообщается, каких файлов она не видит, и что нельзя называть отсутствующим файл или изменение, которых она не видит, поэтому сводка не утверждает, что кода нет.

## Настройка

### Один раз на аккаунт: GitHub App для ревьюера

1. Откройте **Settings → Developer settings → GitHub Apps → New GitHub App**.
2. Задайте имя и логотип. В разделе **Webhook** снимите галочку **Active**.
3. В **Repository permissions** выставьте **Contents: Read and write**, **Issues: Read and write** и **Pull requests: Read and write**. Для закрытия обсуждений GitHub требует право записи Contents. При обновлении существующего приложения примите новое право в настройках установки. С Contents read-only ревью и approve продолжают работать, но бот не сможет закрывать исправленные обсуждения.
4. Создайте приложение. Запишите его **Client ID** (начинается с `Iv`) и сгенерируйте **private key**.
5. Чтобы пользоваться приложением в организации, включите **Advanced → Make public** и установите его на организацию. Приватный ключ при этом не раскрывается.

### Для каждого репозитория

1. **Install App** → добавьте репозиторий в установку.
2. В **Settings → Secrets and variables → Actions** добавьте:
   - секрет `DEEPSEEK_API_KEY`;
   - секрет `REVIEW_APP_PRIVATE_KEY`: PEM-файл целиком;
   - переменную `REVIEW_CLIENT_ID`.

   В организации на платном тарифе или для публичных репозиториев их можно задать один раз на уровне организации. На GitHub Free приватные репозитории не видят секреты организации.
3. Добавьте файл `.github/workflows/deepseek-review.yml`:

```yaml
name: DeepSeek PR Review

on:
  pull_request_target:
    types: [opened, reopened, ready_for_review, synchronize, edited]

permissions: {}

concurrency:
  group: deepseek-review-${{ github.event.pull_request.number }}${{ github.event.action == 'edited' && !github.event.changes.base && '-edit' || '' }}
  cancel-in-progress: ${{ github.event_name != 'pull_request_review_thread' }}

jobs:
  review:
    if: github.event.action != 'edited' || github.event.changes.base
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: devnullexile/deepseek-review@v1
        with:
          deepseek-api-key: ${{ secrets.DEEPSEEK_API_KEY }}
          client-id: ${{ vars.REVIEW_CLIENT_ID }}
          app-private-key: ${{ secrets.REVIEW_APP_PRIVATE_KEY }}
          # Необязательно:
          # allowed-authors: alice, bob
          # approve: "false"
          # extra-instructions: |
          #   Check that every user-facing string exists in both locales.
```

Триггер `edited`, условие задания и группа конкурентности `-edit` запускают ревью заново, когда у PR меняется базовая ветка, например когда PR из стека переводят на другую ветку: diff меняется без нового коммита, и без этого прежнее одобрение осталось бы в силе. Правка заголовка или описания не запускает ревью и не отменяет уже идущее.

`pull_request_target` запускает workflow из базовой ветки и даёт ему доступ к секретам, даже для PR из форков. Здесь это безопасно только потому, что код из PR не выполняется. Не добавляйте шаг, который скачивает и запускает код из PR.

## Файлы с данными

Lock-файлы, JSON Lines, CSV и минифицированные файлы, а также файлы JSON, YAML, XML и TOML, в которые добавлено больше `data-file-lines` (1000) строк, в ревью модели не попадают. Они остаются в PR: ничего не переносится и не удаляется. Модель не может осмысленно проверить такие файлы, а большой файл занимает всё окно токенов, и код остаётся без ревью. Комментарий с итогом перечисляет их, чтобы их посмотрел человек, и они не мешают approve, как и `ignore-globs`. Путь из `approval-excluded-paths` проверяется всегда. Выключить: `skip-data-files: "false"`.

Для очень большого изменения GitHub не присылает diff, а файл больше 1 МБ отдаёт без содержимого. Тогда pr-agent показал бы такой файл удалённым или добавленным целиком, и модель проверяла бы неверный diff. Такой файл тоже не попадает в ревью модели, какого бы типа он ни был. Комментарий с итогом называет его, чтобы его проверил человек, и он мешает approve бота, потому что его код никто не проверил.

## Ревью по запросу

По умолчанию проверяется каждый новый коммит (`review-on: push`). Для большого PR, который проходит много кругов исправлений, задайте `review-on: label`. Тогда PR проверяется, когда его открыли, открыли заново, пометили готовым к ревью или сменили базовую ветку, а дальше только когда кто-то добавит метку `review`: на странице PR нажмите **Labels** в правой колонке и выберите `review`, или выполните `gh pr edit <номер> --add-label review`. Бот снимает метку в начале ревью, поэтому, чтобы проверить последний коммит ещё раз, метку нужно добавить снова. Новый коммит без метки снимает approve бота со старых коммитов, и комментарий с итогом об этом сообщает. Метку нужно один раз создать в **Issues → Labels → New label**, а в список событий workflow добавить `labeled`:

```yaml
on:
  pull_request_target:
    types: [opened, reopened, ready_for_review, synchronize, edited, labeled]
```

Если `labeled` есть в списке, метка `review` запрашивает ревью и в режиме `push` по умолчанию.

Чтобы обновлять итоговый комментарий и approve после закрытия или повторного открытия обсуждения человеком, можно добавить в тот же workflow событие ниже. Оно перепроверяет уже просмотренный коммит без вызова модели по состоянию в итоговом комментарии (`result-comment: "true"` по умолчанию). Для PR из форка это событие может не получить секреты приложения; тогда бот пропустит перепроверку без ошибки.

```yaml
on:
  pull_request_review_thread:
    types: [resolved, unresolved]

concurrency:
  group: deepseek-review-${{ github.event.pull_request.number }}${{ github.event.action == 'edited' && !github.event.changes.base && '-edit' || '' }}
  cancel-in-progress: ${{ github.event_name != 'pull_request_review_thread' }}
```

Существующий триггер `pull_request_target` нужно сохранить. Без нового события открытые обсуждения перепроверяются при следующем полном ревью. Сохраните показанную настройку конкурентности: событие, созданное самим ботом, будет ждать завершения текущего ревью и не отменит его.

## Требования к раннеру

Нужен Linux-раннер с Docker и Python 3. На раннерах GitHub `ubuntu-latest` есть и то и другое.

## Чьи PR проверяются

По умолчанию проверяются PR от владельцев репозитория, членов организации и коллабораторов. Каждое ревью тратит токены DeepSeek, а так посторонние не смогут расходовать ваш ключ. Чтобы перечислить конкретные логины, задайте `allowed-authors`. Скрытых членов организации GitHub может помечать как `CONTRIBUTOR`, и тогда правило по роли их пропустит.

Чтобы проверять только членов организации, которой принадлежит репозиторий, задайте `members-only: "true"`. Членство тогда проверяется через GitHub API: скрытые члены учитываются, внешние коллабораторы — нет. Логины из `allowed-authors` тоже проверяются. Приложению ревьюера нужно право организации **Members: Read-only**: добавьте его в **Permissions & events** приложения и примите новое право в настройках установки в организации.

## Параметры

| Параметр | По умолчанию | Значение |
|---|---|---|
| `deepseek-api-key` | обязателен | Ключ DeepSeek API |
| `client-id` | обязателен | Client ID приложения GitHub App ревьюера; подходит и числовой App ID |
| `app-id` | пусто | Устарел: числовой App ID, используется, если `client-id` пуст. Используйте `client-id` |
| `app-private-key` | обязателен | Приватный ключ GitHub App ревьюера |
| `allowed-authors` | пусто | Логины для ревью; если пусто — владельцы, члены организации и коллабораторы |
| `request-changes` | `false` | Ставить «request changes» при вердикте `changes_required`; полезно вместе с защитой веток |
| `members-only` | `false` | Ревьюить только членов организации-владельца (нужно право Members: Read-only) |
| `approve` | `true` | Ставить approve чистым ревью и снимать устаревшие approve бота |
| `approval-excluded-paths` | `.github/*` | Маски файлов, которые бот никогда не одобряет, только человек. `*` совпадает и с `/`. Пусто — разрешить любые пути |
| `extra-instructions` | пусто | Правила проекта, которые добавляются к общей политике ревью |
| `ignore-globs` | пусто | JSON-массив масок файлов, которые не проверять, например `'["*.meta", "*.unity"]'`; такие файлы не ревьюятся и не мешают approve |
| `skip-data-files` | `true` | Не отдавать модели [файлы с данными](#файлы-с-данными); они перечислены в комментарии с итогом |
| `data-file-lines` | `1000` | Сколько добавленных строк нужно, чтобы файл JSON, YAML, XML или TOML считался данными |
| `max-previous-findings-chars` | `60000` | Сколько символов прежних замечаний и ответов в их закрытых обсуждениях видит модель, чтобы не повторять их; у pr-agent по умолчанию 8000, `0` выключает |
| `result-comment` | `true` | Поддерживать один комментарий с решением бота и его причинами |
| `converge` | `true` | После первого ревью блокировать только замечаниями на изменённом с прошлого ревью коде и открытыми обсуждениями бота |
| `max-blocking-reviews` | `3` | Сколько ревью одного PR могут блокировать замечаниями модели; последующие только публикуют их. `0` — без ограничения |
| `resolve-fixed-threads` | `true` | Закрывать обсуждения бота, строки которых изменил следующий коммит, если новое ревью ничего там не повторило |
| `review-on` | `push` | `push` проверяет каждый коммит; `label` проверяет новые коммиты только после добавления метки (см. [Ревью по запросу](#ревью-по-запросу)) |
| `review-label` | `review` | Метка, которая запрашивает ревью последнего коммита; бот снимает её в начале ревью |
| `model` | `deepseek/deepseek-flash` | Имя модели в LiteLLM; это DeepSeek-V4.1-Flash |
| `max-model-tokens` | `512000` | Окно токенов на вызов; на вход остаётся то, что не занято `max-output-tokens` (по умолчанию 128K) |
| `max-output-tokens` | `384000` | Лимит выходных токенов на вызов, включая размышления модели; для моделей с меньшим лимитом уменьшите его вместе с `max-model-tokens` |
| `response-language` | `en-US` | Язык ревью |
| `max-findings` | `5` | Максимум замечаний |
| `pr-agent-image` | `pragent/pr-agent:0.49.0` | Образ pr-agent; шаг approve зависит от формата его `--json-output` |
| `review-attempts` | `2` | Сколько попыток, если обзор упал или не записал читаемый результат; `1` отключает повторы. Каждая попытка может снова обратиться к модели |
| `retry-delay-seconds` | `30` | Пауза перед повтором упавшей попытки |
| `fallback-models` | `[]` | JSON-массив моделей, которые pr-agent пробует по порядку, если основная модель упала в рамках попытки; пустой массив — без запасных |

Выходы: `reviewed` (`true`, если ревью было) и `approval` (`approved`, `already-approved`, `changes-requested`, `already-changes-requested`, `no-concerns`, `not-approved`, `head-changed`).

## Версии

Указывайте `@v1`, чтобы получать совместимые обновления, или полный SHA коммита, чтобы зафиксировать точную версию. Смена образа pr-agent или правил approve выходит новой major-версией.

## Разработка

```sh
python3 -m unittest discover -s tests -v
```

Контрактным тестам `action.yml` нужен PyYAML; без него они пропускаются.

Логика approve находится в `scripts/review_gate.py` и использует только стандартную библиотеку Python.
